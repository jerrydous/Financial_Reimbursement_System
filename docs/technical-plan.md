# 技术计划

## 1. 目标基线

**要做成：** 单企业、单账套可运行的费控闭环。员工提交对私报销，系统采集发票、执行标准和预算、走审批、财务审核、出纳确认支付，并留下不可改的审计记录。

**成功标准：**

- 一条真实路径可走完：登录 → 上传发票 → 确认识别结果 → 提交报销单 → 主管审批 → 财务审核 → 出纳支付 → 单据与预算、发票状态正确。
- 金额全程以「分」为整数。同一张增值税发票不能进入两张有效报销单。
- 审批、驳回、撤回、支付都可追溯到操作者、时间和前后状态。
- 类型检查、lint、测试、迁移和核心集成测试在 CI 通过。
- README 能按步骤启动 Docker Compose 并跑通上述路径。

**本阶段不做：** 多租户计费、税局勾选认证、自研 OCR、自研会计引擎、自研 BPM、商旅自动下单、手写签名、信用分抽审、Kubernetes、按服务拆仓。表上保留 `tenant_id`，默认一个租户。

目标变更必须写成新版本基线。实现 AI 不得在编码时悄悄加一期范围，或把后期功能塞进当前切片。

## 2. 构建方法

报销要解决的是：员工垫付或对公支出，经过申请、发票、标准、预算和审批，变成可审计的付款。对象是申请单、费用、发票、借款、预算、审批、付款。这些边界在企业费控里是稳定的。

功法《系统构建》写明：目标清楚、边界稳定、规模偏 ERP/审批的系统，设计从整体拆到模块。企业内部审批的例子也是先定表单、流程、权限、通知、记录、报表。

因此本系统：

1. **设计走自顶向下。** 先冻结目标基线、限界上下文、状态机、金额不变量和验收标准，再写代码。
2. **拆分走分而治之。** 按业务能力切垂直切片。每一片同时交付契约、表结构、API、页面和测试。
3. **实现里的自底向上只表示接通顺序。** 先把身份、数据库、对象存储、工作流、规则引擎跑通一条冒烟路径，再编排进第一张报销单。这些能力来自成熟产品。
4. **不采用的构建方式：** 先自研一套平台组件，再往上长业务。功法指出这种自底向上会变成「组件很多，系统拼不起来」。拼好码同时禁止把通用能力再写一遍。

交付顺序是垂直切片，不是「先全部表，再全部接口，再全部页面」。

## 3. 功能范围

能力对照每刻报销的公开产品能力。

| 每刻公开能力 | 本系统落点 | 阶段 |
|---|---|---|
| 对私报销提单 | 报销单、费用明细、附件 | P1 |
| 智能识票，一键生成费用 | 官方 OCR 适配器 + 人工确认 | P1 |
| 移动审批、审批日志 | 响应式 Web；同意、驳回、转交、撤回 | P1 单线；P3 完整 |
| 财务审核、金额/科目调整 | 财务岗可改批准金额和科目，保留原值 | P1 |
| 出纳付款 | 付款单、支付结果回写 | P1 |
| 关联申请、申请额度 | 事前申请占用，报销不得超过剩余额度 | P2 |
| 费用标准、超标强控/弱控 | 规则引擎 + 版本化制度 | P2 |
| 补贴计算 | 按城市、职级、天数的规则，生成补贴费用 | P2 |
| 借款与冲销 | 借款余额、报销核销、超期未还拦截 | P2 |
| 会签、或签、条件分支、代理、超时 | Temporal 编排，代理人配置 | P3 |
| 费用拆分、费用分摊 | 按部门/项目/成本中心，尾差归最大行 | P4 |
| 多维预算：部门、项目、科目、期间 | 事前冻结、事中拦截、事后查询 | P4 |
| 发票验真、查重、抬头、税号、印章 | 查验适配器 + 数据库唯一约束 | P5 |
| 发票类型/时间/金额与费用、行程匹配 | 智能审核规则，强控或弱控 | P5 |
| 发票台账 | 查询、导出 | P5 |
| 报销及时性、跨年、逾期 | 规则引擎 | P5 |
| 对公到票、付款、合同、分期 | 独立聚合，复用审批和预算 | P6 |
| 凭证导出（用友/金蝶一类） | 只写适配器 | P6 |
| 商旅订单导入（携程、滴滴一类） | 只写订单到费用的适配器 | P6 |
| 发票袋、档案系统、进项勾选认证 | 文件进对象存储；认证只导出待认证清单 | 不做全功能 |
| 信用调整、整单免票、手写签名 | 有审计和规则后再加 | 不做 |

智能审核第一版是可版本化的规则，每条给出通过、警告或阻断。本期不训练、也不托管审核模型。

## 4. 技术栈

选型来自功法技术栈里的两类成熟组合：后台管理用 React + TypeScript + Ant Design；结构化业务数据用 TypeScript + PostgreSQL + Prisma。前后端统一 TypeScript。

| 层 | 锁定技术 | 胶水职责 |
|---|---|---|
| 语言 | TypeScript `strict`，Node.js 22 LTS | 类型即部分契约 |
| 仓库 | pnpm workspace | 应用与契约分包 |
| Web | Vite、React、React Router、Ant Design、TanStack Query、React Hook Form、Zod | 页面和字段编排 |
| API | NestJS | 路由、守卫、管道、事务边界 |
| 数据 | PostgreSQL 16、Prisma | 约束、迁移、金额真相 |
| 缓存 | Redis | 幂等键缓存、限流；不是金额真相 |
| 耐久流程 | Temporal + 官方 TypeScript SDK | 审批等待、超时、补偿 |
| 异步任务 | BullMQ | OCR、通知、导出；不承载付款状态 |
| 规则 | json-rules-engine | 差标、智能审核、超标强弱控 |
| 身份 | Keycloak OIDC | 登录与身份源 |
| 授权 | Casbin | 本人/部门/抬头/财务的数据范围 |
| 文件 | MinIO，`@aws-sdk/client-s3` | 发票原件 |
| 识票 | 云厂商增值税发票 OCR 官方 SDK | 映射成费用草稿 |
| 查验 | 发票查验官方 API | 结果写入台账 |
| 表格 | exceljs | 台账与付款清单 |
| 日志 | pino、OpenTelemetry | 请求与工作流关联 |
| 测试 | Vitest、Supertest、Testcontainers、Playwright | 门禁证据 |
| 质量 | ESLint、Prettier、tsc、GitHub Actions、密钥扫描 | 机器执行 |
| 本地 | Docker Compose | postgres、redis、minio、keycloak、temporal、api、worker、web |

第一期不进入技术栈的有：Kubernetes、微服务拆分、Kafka、Elasticsearch、自研规则语言、自研流程引擎。列表搜索用 PostgreSQL。

## 5. 胶水映射

本仓库只写连接、适配、编排、配置、业务不变量和测试。

| 需求 | 必须复用 | 本仓库只写 |
|---|---|---|
| 登录、密码、令牌、身份源 | Keycloak；企微/钉钉/飞书走 Identity Brokering | 外部 subject 映射到员工 |
| 审批等待、超时、重试、历史 | Temporal | 同意/驳回/转交信号；会签与或签的编排 |
| 制度判断 | json-rules-engine | 规则 JSON 的版本、发布、启停 |
| 识票 | 官方 OCR SDK | 文件到草稿、置信度低则人工确认 |
| 验真 | 官方查验 API | 超时、退避、结果落库 |
| 文件 | S3 API | 对象键、授权下载 |
| 数据范围 | Casbin | 模型文件与策略数据 |
| 导出 | exceljs | 列定义 |
| 通知 | 邮件或企微/钉钉官方 SDK | 触发点与模板参数 |
| 金额运算 | `bigint` 分 | 分摊尾差、冲销、额度 |
| 主键 | UUID v7 库 | 不自写随机数 |

生成代码时，文件头用一行注释标明外部依赖，例如：`// 耐久等待来自 @temporalio/workflow，本文件只发信号`。

### 允许手写的业务差异

只有这些可以在 `packages/domain` 里实现，并且必须有单测：

- 申请、报销、借款、付款的状态迁移表
- 以分为单位的额度、批准金额、核销和分摊尾差
- 预算冻结、转消耗、释放的事务不变量
- 一张发票只能绑定一张有效单据
- 报销金额、发票价税合计、申请剩余额度之间的匹配
- 强控阻断提交，弱控允许提交但留下警告

除此之外的自研，先写 `docs/adr/` 偏离说明，否则停止实现。

### 目录

```text
apps/web          页面。不得导入 Prisma 或第三方 OCR SDK
apps/api          HTTP、事务、鉴权。不得承载流程等待
apps/worker       Temporal Worker 与 BullMQ。活动函数调用领域服务
packages/contracts  Zod 契约，API 与前端的单一来源
packages/domain   纯函数与不变量。无网络、无数据库客户端
packages/adapters OCR、查验、存储、通知、身份声明解析
```

依赖方向：`web → contracts`；`api/worker → domain、contracts、adapters`；`domain` 不依赖 Nest、Prisma、Temporal、Ant Design 和任何 SDK。适配器文件内部直接调用官方 SDK 的真实 API，不再包一层简化版 SDK。

## 6. 领域边界与状态

上下文：身份与组织、主数据、申请、费用与发票、借款、报销、审批编排、预算、付款、审核规则、审计。

| 单据 | 状态 |
|---|---|
| 申请单 | draft → submitted → approving → approved / rejected / withdrawn → closed |
| 报销单 | draft → submitted → approving → finance_review → paying → paid；旁路 rejected、withdrawn |
| 借款单 | draft → approving → outstanding → settled |
| 预算占用 | reserved → consumed；reserved → released |
| 付款单 | pending → succeeded / failed |

已支付单据不可改金额。财务调整只发生在 `finance_review`，写入调整记录，保留员工原始金额。取消用状态表达。财务单据不做物理删除，也不做静默软删除。

主数据：员工、部门、岗位、职级、公司抬头、成本中心、项目、供应商、费用类型、预算科目。员工只能使用已启用且属于自己数据范围的抬头和部门。

## 7. 金额与并发不变量

- 持久化金额是 `bigint` 分。币种用 ISO 4217，默认 `CNY`。
- API 传输金额用字符串形式的整数分。展示层再格式化成元。
- 禁止 `number`、`float`、`double`、JavaScript `Number` 参与加减和比较。
- 分摊：按比例算到分，尾差加到金额最大的一行。冲销同样处理。
- 创建报销、冻结预算、确认支付必须带 `Idempotency-Key`。数据库有唯一约束，Redis 只作加速。
- 预算变更在同一数据库事务内对预算行 `SELECT … FOR UPDATE`。
- 单据带 `version`。更新使用比较并交换，冲突返回 409。
- 发票唯一键：租户 + 发票代码 + 发票号码；数电票用发票号码。再加文件哈希，捕捉重复影像。
- 审计表只追加。应用数据库角色没有审计表的 UPDATE 和 DELETE。

## 8. 切片验收

**P0 骨架。** Compose、Keycloak 登录、员工与公司抬头、空报销列表、CI、`.env.example`。验收：未登录被拒绝；登录后只看到自己的员工身份。

**P1 对私闭环。** 上传发票、OCR 草稿、人工确认、报销单、单线审批、财务改批准金额、出纳确认支付、审计。验收：重复提交不产生第二张单；驳回后可修改再提；支付成功后金额不可改。

**P2 费控。** 申请额度、差标强弱控、补贴、借款与冲销、逾期未还拦截。验收：超额度与强控差标不能提交；弱控能提交且审核队列看得到警告；冲销不超过借款余额。

**P3 审批。** 会签、或签、条件分支、代理、转交、撤回、超时提醒。验收：或签一人通过即前进；会签必须全员通过；代理期间原审批人与代理人的权限符合规则；撤回仅在无人通过前成功。

**P4 分摊与预算。** 多维预算的冻结、消耗、释放。验收：并发提交不能把同一预算行打成负数；驳回和撤回释放冻结；支付把冻结转为消耗。

**P5 发票合规与台账。** 验真、抬头税号、类型/时间/金额匹配、及时性、导出台账。验收：查重靠数据库约束；查验超时可重试且不会重复入账。

**P6 对公与外部系统。** 到票付款、凭证导出适配器、商旅订单导入适配器。无真实沙箱时，适配器契约测试用记录下来的官方响应样例，生产模块仍调用真实 SDK 入口。

已预批的唯一简化：P1 可以没有真实查验沙箱，但发票状态只能是「未验真」，不能显示「验真通过」。

## 9. 偏离协议

若确实不能用第 4 节的库，先写 `docs/adr/NNN.md`，包含：原因、评估过的成熟方案、不满足的约束、自研边界、维护成本、安全风险、测试、替换与回滚。没有这份记录，审查结论为 BLOCK。
